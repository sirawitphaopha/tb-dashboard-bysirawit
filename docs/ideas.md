## 1. Responsive — จอความละเอียดต่ำ ปุ่มโดนตัด/กลืน
- **วันที่คิด:** 2 ก.ค. 2569
- **วันที่ทำจบ:** — (ยังไม่เสร็จ)
- **สถานะ:** ยังไม่เริ่ม

### อาการที่ผู้ใช้เจอ (เก็บครบ)
- ที่จอความละเอียด **768p** (สูง 768px เช่น 1366×768 ที่พบบ่อยในโน้ตบุ๊ก/คอมโรงพยาบาล) **บางปุ่มโดนตัดหรือถูกกลืนหายไป**
- ที่จอ **1080p** (1920×1080) แสดงผลปกติ ไม่มีปัญหา
- แปลว่าปัญหาเกิดเฉพาะ **จอเตี้ย/ความละเอียดต่ำ**

### วิเคราะห์ประเด็น (Claude เสริม)
- layout ปัจจุบันน่าจะออกแบบมาเผื่อจอ 1080p เป็นหลัก พอเจอจอเตี้ยพื้นที่ไม่พอ ปุ่ม/แถบเครื่องมือเลยล้นหรือถูกตัด
- จุดที่มักมีปัญหา: แถว action ปุ่มเยอะ ๆ, toolbar, modal ที่สูงเกินจอ, header/footer ที่ fix ความสูง
- แนวทางที่เป็นไปได้: ปรับ responsive breakpoint, ให้ปุ่มขึ้นบรรทัดใหม่ได้ (flex-wrap), ทำ overflow ให้เลื่อนได้แทนโดนตัด, ลดความสูงองค์ประกอบบนจอเตี้ย

### คำถามค้างก่อนลงมือ
- ปุ่ม/หน้าไหนบ้างที่โดนตัด (อยากได้รูปหรือชื่อหน้าเจาะจง จะได้ไล่แก้ตรงจุด)
- อยากให้รองรับความละเอียดต่ำสุดที่เท่าไร (เช่น 1366×768 หรือเล็กกว่านั้น)

## 2. ต้องเปิดได้บน Windows 7 (เบราว์เซอร์เก่าในโรงพยาบาล)
- **วันที่คิด:** 2 ก.ค. 2569
- **วันที่ทำจบ:** — (ยังไม่เสร็จ)
- **สถานะ:** ยังไม่เริ่ม

### ที่มา (เก็บครบ)
- คอมบางเครื่องในโรงพยาบาลยังเป็น **Windows 7**
- เบราว์เซอร์บนเครื่องพวกนั้นเก่า → **ไม่รองรับกราฟฟิก/ฟีเจอร์บางอย่าง** ของเว็บ

### วิเคราะห์ประเด็น (Claude เสริม)
- เว็บใช้ Next.js 16 + React 19 + ฟีเจอร์ CSS/JS สมัยใหม่ ซึ่งเบราว์เซอร์เก่าอาจรันไม่ได้
- จุดที่น่าจะมีปัญหาบนเบราว์เซอร์เก่า: การถอดรหัสรูป HEIC (ใช้ wasm), Chart.js, CSS สมัยใหม่ (grid/flex gap, backdrop-filter), และฟีเจอร์ JS ใหม่ ๆ
- แนวทาง: ตรวจว่าอะไรพังบ้าง แล้วทำ **graceful degradation / fallback** ให้ใช้งานหลักได้แม้กราฟฟิกบางอย่างหาย
- เกี่ยวโยงกับข้อ 3 (scrollbar auto-hide อาจใช้ CSS/JS ที่เบราว์เซอร์เก่าไม่รองรับ ต้องเผื่อ fallback)

### คำถามค้างก่อนลงมือ (สำคัญมาก)
- เครื่อง Win 7 พวกนั้นใช้ **เบราว์เซอร์อะไร เวอร์ชันประมาณไหน** (เช่น Chrome/Firefox เวอร์ชันเก่าสุดที่ Win 7 ลงได้ราว ๆ Chrome 109 / Firefox 115, หรือถ้าเป็น IE/Edge เก่าจะยิ่งมีข้อจำกัด)
- อาการ "กราฟฟิกไม่ขึ้น" ที่เจอ เป็นตรงไหนของเว็บบ้าง

## 3. Scrollbar ฝั่งขวา — ซ่อนตอนไม่ได้เลื่อน (auto-hide)
- **วันที่คิด:** 2 ก.ค. 2569
- **วันที่ทำจบ:** — (ยังไม่เสร็จ)
- **สถานะ:** ยังไม่เริ่ม

### อาการที่ผู้ใช้เจอ (เก็บครบ)
- ตอนนี้แถบเลื่อน (scrollbar) ฝั่งขวา **ค้างแสดงตลอด** ในบางหน้า
- อยากให้แสดง **เฉพาะตอนกำลังเลื่อนเพจ** (ขึ้น/ลง) — ถ้าไม่เลื่อน ให้ซ่อนหายไป

### วิเคราะห์ประเด็น (Claude เสริม)
- พฤติกรรมที่ต้องการคือ **overlay / auto-hide scrollbar** แบบ macOS (โผล่ตอนเลื่อน แล้วค่อย ๆ จางหาย)
- แนวทางที่เป็นไปได้:
  - CSS: `scrollbar-gutter`, `::-webkit-scrollbar` ปรับหน้าตา (แต่คุม "ซ่อนตอนไม่เลื่อน" ได้จำกัด)
  - JS: จับ event `scroll` แล้วโชว์ scrollbar, ตั้ง timer ให้ซ่อนเมื่อหยุดเลื่อน
- ต้องระวังอย่าให้เกิด **layout shift** ตอน scrollbar โผล่/หาย (เนื้อหาขยับ)
- ⚠️ ต้องเช็คให้เข้ากับ **เบราว์เซอร์เก่า (ดูข้อ 2)** — บางเทคนิคเบราว์เซอร์เก่าไม่รองรับ

### คำถามค้างก่อนลงมือ
- หน้าไหนบ้างที่ scrollbar ค้าง (ทั้งเว็บ หรือเฉพาะบางหน้า/บาง modal)
- เอาแบบซ่อนสนิทตอนไม่เลื่อน หรือให้จางบาง ๆ ค้างไว้

## 4. หน้า Wiki (แถบเมนูซ้าย) — คู่มือการใช้งาน + คลังโลจิก + พิพิธภัณฑ์หน้าตาเว็บ
- **วันที่คิด:** 2 ก.ค. 2569
- **วันที่ทำจบ:** — (ยังไม่เสร็จ)

### ที่มา / แนวคิดหลัก (ตามที่ผู้ใช้เล่า — เก็บครบทุกจุด)
- เพิ่มหน้าใหม่เข้าไปใน **แถบเมนูฝั่งซ้าย (sidebar)** ชื่อหน้าว่า **"wiki"**
- หน้านี้เป็น **"ที่จด"** รวมทุกอย่างเกี่ยวกับเว็บไว้ที่เดียว โดยตั้งใจให้เก็บ 3 อย่างหลัก:
  1. **วิธีการใช้เว็บ** — คู่มือว่าแต่ละหน้า/แต่ละปุ่มใช้ยังไง ทำอะไรได้บ้าง
  2. **คำอธิบายโลจิกต่าง ๆ** — อธิบายว่าเบื้องหลังระบบทำงานยังไง (เช่น การอนุมัติผู้ใช้, ระบบถังขยะ, การลบรูป ฯลฯ)
  3. **หน้า mockup (จำลอง)** ของหน้าจอที่จะขึ้นใน **สถานการณ์ต่าง ๆ** — เช่น หน้าเมื่อรออนุมัติ, หน้าเมื่อถูกปฏิเสธ, หน้าตอน error, popup แจ้งเตือนต่าง ๆ

### กติกาสำคัญของหน้านี้ (จุดที่ผู้ใช้เน้นมาก)
- **ทั้งหมดห้ามแปะเป็น "รูปภาพ"** — ให้ **เขียนด้วย HTML จำลองหน้าเว็บจริง** แทน
- เขียน HTML เพื่อ **จำลองหน้าเว็บเก่า ๆ** ขึ้นมาใหม่ ให้หน้าตาเหมือนของจริงในอดีต
- เหตุผลที่ต้องเป็น HTML ไม่ใช่รูป:
  - **ดูย้อนอดีตได้** ว่าแต่ก่อนหน้าตาเว็บเป็นยังไง (เหมือนไทม์แคปซูล / พิพิธภัณฑ์เวอร์ชันเก่า)
  - เอาไว้ **แปลงโลจิกจาก code → เป็นประโยคภาษาคน + วิธีการใช้งาน** ที่อ่านเข้าใจง่าย ไม่ใช่ต้องไปนั่งอ่าน code

### ภาพเปรียบเทียบที่ผู้ใช้ให้ไว้
- เหมือน **"สมุดคู่มือเล่นเกม"** ที่มี **ภาพประกอบ** ให้ดู
- และมี **"ประวัติการสร้างเกม"** (development history) เล่าให้อ่านด้วย
- → คือทั้ง *คู่มือใช้งาน* + *บันทึกประวัติการพัฒนา* อยู่ในเล่มเดียว

### ทำไมไอเดียนี้ต่อยอดจากของเดิมได้พอดี
- ตอนนี้เว็บ **มีประวัติเวอร์ชันแบบภาษาคน (changelog) ให้อ่านเล่น ๆ อยู่แล้ว** (`app/legacy/tb-changelog.js` ที่ auto-gen จาก git log)
- หน้า wiki จะเป็น **ส่วนขยายที่ลึกกว่า changelog** — changelog บอกว่า "เวอร์ชันนี้เปลี่ยนอะไร" ส่วน wiki จะเก็บ *หน้าตาจริง ๆ ของแต่ละยุค* + *อธิบายว่าทำไม/ทำงานยังไง*

### ไอเดียต่อยอดเพิ่มเติม (ผมเสริมให้ — ยังไม่ใช่ข้อสรุป รอผู้ใช้ตัดสินใจ)
- **จัดเป็นหมวด/ไทม์ไลน์** — แบ่ง wiki เป็นแท็บ เช่น "วิธีใช้งาน" / "อธิบายโลจิก" / "แกลเลอรีหน้าเก่า (ตามเวอร์ชัน)"
- **ผูกกับเลขเวอร์ชัน** — mockup แต่ละอันติดป้ายว่าเป็นหน้าตาของเวอร์ชันไหน (เช่น "หน้า login v0.6.x") จะได้เห็นวิวัฒนาการเรียงตามเวลา
- **snapshot HTML แบบ self-contained** — เก็บ HTML ของหน้าเก่าไว้เป็นไฟล์นิ่ง ๆ ไม่ผูกกับ component ปัจจุบัน (เพื่อไม่ให้พังเวลาโค้ดจริงเปลี่ยน) — เหมือนถ่ายรูปแต่เป็นโค้ดที่ยังกดเล่นได้
- **เข้าถึงเฉพาะแอดมิน หรือเปิดให้ทุกคน** — ต้องตัดสินใจว่าใครเห็นหน้า wiki ได้บ้าง
- **ทำเป็น mockup แบบกดได้ (interactive) หรือแค่โชว์เฉย ๆ** — ต้องเลือกระดับความละเอียด

### สิ่งที่ต้องเคาะก่อนลงมือ (คำถามค้าง)
- หน้า wiki นี้ให้ใครเข้าได้ (แอดมินเท่านั้น / ทุกคน)
- อยู่ตรงไหนของ sidebar และชื่อเมนูภาษาไทยว่าอะไร (คำว่า "wiki" หรือแปลไทย)
- เริ่มจากเก็บย้อนหลังกี่เวอร์ชัน หรือเริ่มเก็บตั้งแต่ตอนนี้เป็นต้นไป

- สถานะ: ยังไม่เริ่ม

## 5. แท็บ "ความรู้วัณโรค" — คลังไกด์ไลน์ + Trial + บทความเขียนเอง (พร้อมระบบอ่าน PDF ในเว็บ)
- **วันที่คิด:** 2 ก.ค. 2569
- **วันที่ทำจบ:** — (ยังไม่เสร็จ)

### สถานะปัจจุบัน
- ในเว็บ**มีแท็บ "ความรู้วัณโรค" อยู่แล้ว แต่ยังใช้งานไม่ได้** — ตอนนี้มีแค่หัวข้อ/เมนูตั้งไว้เฉย ๆ ยังไม่มีเนื้อหาข้างใน

### สิ่งที่ผู้ใช้คิดไว้ (เก็บครบทุกจุด)
**A. ไกด์ไลน์ (Guideline) และ Trial แบบลิงก์ต้นฉบับ**
- ถ้าเป็น **ไกด์ไลน์** หรือ **trial** → กดแล้ว **ไปที่เว็บไซต์ต้นฉบับ** ได้ (เปิดลิงก์ไปแหล่งจริง)

**B. เก็บ PDF ไว้บนคลาวด์ของเว็บเองด้วย**
- นอกจากลิงก์ต้นฉบับ เว็บของเรา **ต้องมีไฟล์ PDF เก็บไว้บนคลาวด์ของเว็บ** (เผื่อต้นฉบับหาย/เข้าไม่ได้)
- **กดอ่าน PDF ได้เลยในเว็บ** — ไม่ต้องโหลดออกไปเปิดข้างนอก
- → ต้อง **เพิ่มระบบอ่าน PDF และแสดงผล (PDF viewer)** ในเว็บ — ผู้ใช้บอกว่า "น่าสนุก" 🙂

**C. เนื้อหาความรู้แบบเขียนเอง (เหมือน Google Doc + Slide)**
- อยากให้ส่วนความรู้เป็น **รูปแบบเหมือน Google Doc + Slide** ที่ **เขียนบทความเองได้**
- คือมี editor ให้พิมพ์/จัดหน้า/ใส่ภาพ ทำเป็นบทความหรือสไลด์ความรู้ได้เอง

**D. Trial แบบ PDF ที่หาโหลดมาเอง**
- นอกจากไกด์ไลน์ จะมี **trial แบบ PDF ที่ผู้ใช้หาโหลดมาเอง** แล้วเอามาอ่านในเว็บ
- และ **มีสรุป trial (ภาษาคน) ให้อ่านด้วย** — ไม่ใช่แค่แปะ PDF แต่มีย่อใจความให้

### โครงสร้างที่เป็นไปได้ (Claude เสริม — รอผู้ใช้เคาะ)
- แบ่งเป็นหมวดใหญ่: **ไกด์ไลน์** / **Trial / งานวิจัย** / **บทความเขียนเอง**
- การ์ดแต่ละชิ้นเก็บ: ชื่อเรื่อง, องค์กร/ปีที่ออก (เช่น WHO, สมาคมอุรเวชช์ฯ, แนวทาง NTP ไทย), ลิงก์ต้นฉบับ, ไฟล์ PDF (กดอ่านในเว็บ), บทสรุปภาษาคน, แท็ก (เช่น ยา, สูตรยา, MDR-TB, latent TB)
- **ค้นหา + กรอง** ตามหมวด/แท็ก/ปี
- **สิทธิ์การใช้งาน**: ใครเขียน/แก้ได้ (แอดมิน) vs ใครอ่านได้ (ทุกคน)

### เรื่องเทคนิคที่ต้องเตรียม (Claude เสริม)
- **ที่เก็บ PDF**: เว็บมี Cloudflare R2 อยู่แล้ว (ใช้เก็บรูปคนไข้/avatar) — ต่อยอดทำ bucket/โฟลเดอร์ "knowledge" เก็บ PDF ได้เลย ไม่ต้องหา service ใหม่
- **ตัวอ่าน PDF**: ต้องเลือก viewer (เช่น pdf.js) และ **ต้องเพิ่ม origin ใน CSP ที่ `next.config.js`** ให้แสดง PDF ได้ (ตามกฎ CLAUDE.md เรื่อง CSP)
- **editor แบบ Doc/Slide**: เป็นฟีเจอร์ใหญ่ ต้องเลือก rich-text/block editor + เก็บเนื้อหาลง DB (ตารางใหม่ เช่น `tb_knowledge_articles`)
- **ขนาดไฟล์ vs โควตา**: PDF ไกด์ไลน์บางอันใหญ่ ต้องดูผลกระทบกับโควตา R2 (10 GB) และหน้า Storage monitor ที่มีอยู่

### ⚠️ จุดที่ต้องระวัง (Claude เสริม — สำคัญ)
- **ลิขสิทธิ์ PDF**: การเอา PDF ไกด์ไลน์/trial (โดยเฉพาะ paywall หรือของวารสาร) มาเก็บบนคลาวด์เราแล้วเปิดให้คนอื่นอ่าน **อาจติดเรื่องลิขสิทธิ์** — ต้องเช็กว่าไฟล์ไหนเผยแพร่ซ้ำได้ (open access) ไฟล์ไหนควรทำแค่ "ลิงก์ไปต้นฉบับ" อย่างเดียว
- แนะนำแยกให้ชัด: **open access → เก็บ PDF ในเว็บได้** / **มีลิขสิทธิ์ → ลิงก์ออกอย่างเดียว หรือเก็บแค่บทสรุปที่เราเขียนเอง**

## 💡 QR Login ข้ามเครื่อง (นึกได้ 5 ก.ค. 69 · ยังอีกนาน)
- **ไอเดีย:** login เครื่องใหม่โดย**แสกน QR** จากเครื่องที่ login อยู่แล้ว (เหมือน WhatsApp Web / LINE) — ไม่ต้องกรอกรหัส
- **กลไก:** เครื่องใหม่โชว์ QR (encode token ชั่วคราว) → เครื่องเก่าเปิดกล้องแสกน + กดยืนยัน → server ออก session ให้เครื่องใหม่
- **ต้องทำ:** หน้าโชว์ QR + รอผลเรียลไทม์ + หน้าแสกน (กล้อง) + endpoint สร้าง token/ยืนยัน/ออก session (Supabase ไม่มี built-in ต้องทำเอง)
- **⚠️ Security สำคัญมาก (ระบบข้อมูลผู้ป่วย):** QR หมดอายุเร็ว (~1 นาที) · ต้องกดยืนยันบนเครื่องเก่า · โชว์ว่ากำลังให้เครื่องอะไร/ที่ไหนเข้า · กัน QR hijack
- **ทางเลือกที่ง่ายกว่า (แก้ pain "ขี้เกียจกรอกรหัส" ได้เลย):** password manager (Chrome จำรหัส autofill) · "จดจำฉัน" + session ยาว · magic link ทางเมล
- **สถานะ:** เก็บไว้เฉยๆ ก่อน · ทำจริงเป็น 0.8+ แบบมีแผน security เต็ม
